# PiAgent Capability Matrix

Date: 2026-05-31
Phase: Phase 0 audit, with Phase 1 Capability Doctor, Phase 2 browser/screenshot updates, Phase 3 run ledger, and Phase 4 Run History UI appended
Scope: capability map plus implemented Doctor, browser, screenshot, artifact, run-ledger, and read-only run-history evidence

This matrix separates real PiAgent wiring from UI text, prompt guidance, external package availability, and backlog ideas. It is intended to guide the next implementation phase without adding more cosmetic controls.

## Status Taxonomy

- `wired`: visible UI or command is connected to backend/runtime/storage and has a clear verification path. It can still depend on credentials, installed tools, or network state; those dependencies must be shown in verification.
- `partial`: some real wiring exists, but the user-facing workflow is incomplete, misleading, or missing important states.
- `missing`: no real UI/API/runtime path was found.
- `external`: available only through an external tool/package/connector concept, not PiAgent-owned app wiring.
- `unsafe-by-default`: possible through full agent/runtime access, but lacking explicit app guardrails, ownership, or UX.
- `backlog`: documented idea or low-priority future work with no current implementation requirement.

## Top Implementation Targets

1. **Capability Doctor and truthful command surface**: current status `wired` as of Phase 1. `/api/capabilities` returns a read-only report, Settings > Configuration renders the doctor, and `/capabilities` opens that section. Remaining validation: keep adding endpoint-level checks as new capabilities are implemented.
2. **Browser/open-url/screenshot workflow**: current status `wired` for safe URL opening and initial-local-URL screenshot capture as of Phase 2. Remaining validation: add console/network capture and request interception if a full browser debugging bridge is needed.
3. **Image and artifact workflow**: current status `partial`. Screenshot and generated-image artifacts are indexed by `/api/artifacts`; remaining work is richer gallery UI, reveal/download actions, paste/drop images, and run-ledger integration.
4. **Long-running run ledger and checkpoints**: current status `partial` with Phase 3 ledger plumbing and Phase 4 Run History UI. Per-session/project runs now have persistent `runId` state, `/api/runs`, and a read-only Configuration panel; remaining work is a real Pi live smoke in the installed desktop app plus richer checkpoint/artifact timelines. Smallest validation: start a long run, switch chats, verify the run continues and only that chat shows progress.
5. **Memory hygiene and feedback learning**: current status `partial`. Stop internal UI option blocks from becoming memory, connect thumbs up/down to a reviewable memory queue, and expose corrections/forgetting clearly. Smallest validation: send a prompt with UI options enabled, then confirm memory/events exclude the internal option block.

## External Dependency Note

Rows marked `wired` for provider auth, image generation, GitHub, advisor, or subagents mean PiAgent has an app-owned path for configuration and invocation. They still require external credentials, installed packages, network access, or local CLI tooling before the success path works. The capability doctor should show those dependencies separately instead of treating the feature as always ready.

## Uncommitted Runtime Note

Rows that cite dirty runtime/session behavior reflect the current uncommitted working tree. Re-audit those rows after the runtime patch is either committed, released, or reverted.

## Phase 1 Guardrails

- Do not add visible controls unless the matrix status can become `wired` or clearly says `external`/`guidance-only`.
- Add tests for every new backend endpoint before wiring the UI button.
- Keep file/process/browser actions scoped to explicit allowlists and owned resources.
- Preserve OpenAI OAuth, provider API keys, settings patch merging, local memory, advisor/subagents, auto-updater, and session/project storage.
